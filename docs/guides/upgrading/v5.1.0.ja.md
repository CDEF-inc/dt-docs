# v5.1.0 へのアップグレード

!!! warning "データベースのマイグレーションに通常より時間がかかる"
    このリリースでは、ポートフォリオ全体のメトリクスのビューを再構築し、2 つの新しいテーブルをバックフィルします。1 つはパッケージメタデータの解決状態のテーブル、もう 1 つはプロジェクトごとの分析タイムスタンプのテーブルです。ビューの再構築は排他ロックを取得するため、ポートフォリオのメトリクスに対するクエリーは再構築が完了するまでブロックされます。再構築にかかる時間は、[保持期間](../../concepts/time-series-metrics.md#daily-partitions-and-bounded-retention)内にある日次のプロジェクトメトリクスのスナップショットの数に比例します。バックフィルにかかる時間は、重複しない PURL の数とアクティブなプロジェクトの数に比例します。

    バックフィルは新しいテーブルにだけ書き込むため、全停止の時間帯は必要ありません。作業を始める前に[起動プローブの猶予時間](../administration/upgrading-instances.md#rolling-upgrade)を引き上げ、マイグレーションの実行中は API サーバーを中断しないでください。

* **ポートフォリオの分析が決まった時刻に実行されなくなりました**。以前のバージョンは、ポートフォリオ全体の分析を 1 日 1 回開始していました。そのため、数分のうちにすべてのプロジェクトの分析実行が作成され、その間に BOM のアップロードによってトリガーされた分析が遅延していました。各プロジェクトは、最後に分析を試みた時刻を保持するようになりました。タスクは継続的に実行され、最後の分析の試行から [`dt.task.portfolio-analysis.max-analysis-age-ms`](../../reference/configuration/properties.md#dttaskportfolio-analysismax-analysis-age-ms)(デフォルトは 24 時間)より長い時間が経過したプロジェクトを取得します。タスクが同時に実行する自身の分析は、最大で [`dt.task.portfolio-analysis.max-in-flight-analyses`](../../reference/configuration/properties.md#dttaskportfolio-analysismax-in-flight-analyses)(デフォルトは 50)までです。この上限はタスクにだけ適用されます。BOM のアップロードや API の呼び出しは上限に関係なく分析を開始し、どの分析も、何によって開始されたかに関係なくそのタイムスタンプを更新します。頻繁に分析されるプロジェクトは、スケジュールによる分析の対象になることはありません。

    !!! warning
        設定に `dt.task.portfolio-analysis.cron` がまだ含まれている場合、API サーバーは起動を拒否します。このプロパティを削除し、2 つの代替プロパティを、デプロイが維持できるスループットに合わせて設定してください。

* **データベースのクエリーがタイムアウトするようになりました**。API サーバーは、60 秒より長く実行される個々のデータベースクエリーを中止します。以前のバージョンではクエリーの実行時間に制限がなかったため、停止したクエリーや暴走したクエリーがコネクションを無期限に占有し、コネクションプールを使い果たすことがありました。タイムアウトに達した API リクエストは、HTTP ステータス `504` で失敗します。

    正当にタイムアウトを超える可能性のある処理は対象外です。主なものは、データベースのマイグレーションと、ポートフォリオ全体のメトリクスの更新です。

    以前は成功していた操作でデプロイがタイムアウトを報告する場合は、[`dt.datasource.query-timeout-ms`](../../reference/configuration/properties.md#dtdatasourcequery-timeout-ms) で上限を引き上げてください。`0` に設定すると、クエリーのタイムアウトは完全に無効になります。タイムアウトが繰り返し発生する場合は、遅い I/O、autovacuum の遅れ、非効率なクエリープランなど、より根本的な問題があることを示しています。値を恒久的に引き上げる必要がある場合は、Issue を報告してください。

* **新しい `X-Total-Count-Type` レスポンスヘッダー**。REST API v1 は、新しい `X-Total-Count-Type` レスポンスヘッダーによって、上限付きの合計件数を伝えられるようになりました。このヘッダーにはフロントエンドからアクセスできる必要があるため、デフォルトの [`dt.cors.allowed-headers`](../../reference/configuration/properties.md#dtcorsallowed-headers) プロパティを上書きしている場合は、このヘッダーを手動で追加する必要があります。上限付きの合計件数は、大規模なデータセットを扱うためのパフォーマンス最適化の手法です。このバージョンでは、`/api/v1/finding`、`/api/v1/finding/grouped`、`/api/v1/finding/project/{uuid}` のエンドポイントだけがこれをサポートしています。

* **Dependency-Track がデフォルトで KEV カタログをミラーリングします**。新しいタスクが、CISA と ENISA の Known Exploited Vulnerabilities カタログを毎日 02:00 UTC にダウンロードします。Dependency-Track は、両方のデータソースを初期状態でオンにします。外向きの通信を制限しているデプロイでは、フィードのホストを許可するか、到達できないデータソースをオフにする必要があります。スケジュールは [`dt.task.kev-mirror.cron`](../../reference/configuration/properties.md#dttaskkev-mirrorcron) で変更します。

* **影響を受けるバージョンの帰属情報の `lastSeen` が `firstSeen` と同じ値になりました**。REST API v1 の脆弱性のレスポンスでは、このフィールドは `affectedComponents[].affectedVersionAttributions[].lastSeen` として公開されています。このフィールドを更新するとミラーリング中に大量の `UPDATE` クエリーが発生していたため、API サーバーはこのフィールドを更新しなくなりました。このフィールドは非推奨として扱ってください。バージョン 5.2 では、このフィールドとそのデータベースの列が削除されます。

* **CycloneDX の VEX エクスポートが影響を受けるコンポーネントを参照するようになりました**。以前のバージョンは、VEX エクスポート内のすべての `vulnerabilities[].affects[].ref` をプロジェクト(`metadata.component`)に設定していたため、分析がどのコンポーネントに適用されるかという情報が失われていました。エクスポートは影響を受けるコンポーネントを参照し、それらのコンポーネントを `components[]` に含めるようになったため、参照はドキュメント内で解決されます。

    これにより、Dependency-Track がエクスポートした VEX を再インポートしたときの動作が変わります。以前のバージョンは、各分析を脆弱性の影響を受けるすべてのコンポーネントに適用していました。現在は、分析はそれが属するコンポーネントにだけ適用されます。

    !!! note
        `affects[].ref` で `metadata.component` を指定している VEX ドキュメントや、BOM-Link を使っている VEX ドキュメントは、引き続きプロジェクト内の影響を受けるすべてのコンポーネントに分析を適用します。1 つの判断がプロジェクト全体に当てはまる場合は、この形式を使ってください。
