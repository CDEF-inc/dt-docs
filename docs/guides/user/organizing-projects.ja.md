# プロジェクトを階層に整理する

プロジェクトはポートフォリオ内にフラットに配置することも、親の下に入れ子にすることもできます。このガイドでは入れ子について、親の設定、親を*コレクションプロジェクト*にすべき場合の判断、3 つの集約モードの選び方を説明します。

基になるモデルとその制約については、[About projects](../../concepts/projects.md) を参照してください。このガイドの操作には、ポートフォリオ管理の権限が必要です。正確な権限の組み合わせについては、リファレンスの [Permissions](../../reference/permissions.md) を参照してください。

## タグか階層か {#tags-or-hierarchy}

タグと階層は、ポートフォリオを整理する方法として役割が重なります。両者は排他的ではありませんが、目安として次のように使い分けると便利です。

- グループ分けが横断的(`pci`、`external-facing`、`team-platform`)で、1 つのプロジェクトが同時に多くのグループに属する可能性がある場合は、**タグ**を使います。
- グループ分けが構造的(複数のサービスで構成される製品、環境ごとに追跡するサービス、リリースごとに追跡するサービス)で、各プロジェクトに自然な親が 1 つある場合は、**階層**を使います。

階層では、アクセス制御が子孫に伝播し、コレクションプロジェクトによる集約も利用できます。タグではどちらもできません。このガイドの残りの部分では、階層について説明します。

## 親を設定する {#set-a-parent}

親はプロジェクトの作成時に設定するか、後から編集して変更します。

1. *Projects* を開いて *Create Project* を選択するか、既存のプロジェクトを開いて *View Details* を選択します。
2. *General* タブで *Parent* フィールドを探し、入力を始めます。ピッカーはポートフォリオを非同期で検索し、そのプロジェクト自身の子孫は候補から除外します。
3. 親を選んで保存します。

## 親をコレクションプロジェクトにする {#make-the-parent-a-collection-project}

通常の親は、独自のコンポーネントと BOM を持ちます。**コレクションプロジェクト**はどちらも持たず、子のメトリクスを組み合わせるためだけに存在します。次のような場合は、コレクションプロジェクトに切り替えます。

- 親が独自の SBOM を持つものではなく、論理的なグループ(`Acme Web Platform`、`Mobile App`)である。
- グループ全体のリスクの数値、脆弱性の数、違反の数をそれぞれ 1 つにまとめたい。
- 親で BOM のアップロードを受け付けたくない。

親をコレクションプロジェクトに変換する(または新たに作成する)には、*Create Project* フォームまたは *Edit Project* フォームの *General* タブで次の操作を行います。

1. *Collection project* をオンにします。*Classifier* フィールドが表示されなくなります。コレクションプロジェクトには分類子がありません。
2. *Project Collection Logic* を選びます([コレクションロジックを選ぶ](#choose-a-collection-logic)を参照)。
3. タグでフィルターするロジックを選んだ場合は、*Collection Tag* の入力欄に入力します。
4. 保存します。

コンポーネントまたはサービスが 1 つでもあるプロジェクトは、Dependency-Track によってコレクションプロジェクトへの変換を拒否されます。トグルを切り替える前に、プロジェクトを空にするか、必要な状態を子にクローンしてください。

## コレクションロジックを選ぶ {#choose-a-collection-logic}

*Project Collection Logic* のドロップダウンには 3 つのモードがあります。親が答えるべき問いに合った意味を持つモードを選びます。

### すべての直接の子を集約する {#roll-up-every-direct-child}

ドロップダウンで *Aggregate direct children* を選びます。このモードは、タグやバージョンに関係なく、すべての直接の子を集約します。

すべての子が対象範囲に含まれ、親にそれらの状態の和集合を反映させたい場合に使用します。典型的なパターンは、製品を表す親の下に、本番環境で稼働しているマイクロサービスごとに子を 1 つずつ置く構成です。

*すべての*子が集計の対象になり、古い子や実験的な子も含まれることに注意してください。古いバージョンの子を多く残している場合は、他の 2 つのモードのいずれかを使用してください。

### タグの付いた子を集約する {#roll-up-children-carrying-a-tag}

ドロップダウンで *Aggregate direct children with tag* を選び、*Collection tag* の入力欄に入力します。集約の対象は、そのタグが付いた直接の子だけになります。

同じ子の集合をさまざまな切り口で分けたい場合に使用します。よくあるパターンは、同じ親の下に複数のコレクションプロジェクト(`prod` のタグ用、`staging` のタグ用、`dev` のタグ用)を作成し、それぞれがその環境の子だけを集約する構成です。

![コレクションプロジェクトの作成](../../assets/images/guides/user/organizing-projects/collection-with-tag.png)

### 各子の最新バージョンを集約する {#roll-up-the-latest-version-of-each-child}

ドロップダウンで *Aggregate latest version children* を選びます。集約の対象は、最新バージョンとしてマークされた直接の子だけになります。

各子に多数のバージョンがあり、親に現在のリリースを反映させたい場合に使用します。新しいリリースへの切り替えは最新バージョンのフラグを 1 回切り替えるだけで済み([プロジェクトのバージョンを管理する](managing-project-versions.md)を参照)、集約は自動的にそれに追従します。

## 構成例 {#worked-patterns}

よく使われる階層の例をいくつか紹介します。

- **製品、サービス、環境。** 製品にはコレクションプロジェクトの親を、各サービスには通常の親を置き、環境(`dev`、`qa`、`prod`)ごとに通常の子を置きます。環境の子にはタグを付けます。環境ごとの集約が必要な場合は、製品のレベルでタグでフィルターするモードを使用します。
- **サービス、バージョン。** サービスごとに最新バージョンのモードを使うコレクションプロジェクトの親を置き、バージョンごとに通常の子を置きます。*Is latest version* を指定して新しいバージョンをクローンすると、集約が自動的に更新されます。
- **チーム、所有するサービス。** チームごとにすべての子を集約するモードを使うコレクションプロジェクトの親を置き、所有する各サービスを子にします。所有者別のレポートや、チーム単位の通知に役立ちます。

## コレクションプロジェクトの子を確認する {#see-the-children-of-a-collection-project}

親を開きます。詳細ページには、*Components*、*Services*、*Dependency Graph* の代わりに *Collection Projects* タブが表示され、集約に寄与している子が子ごとのメトリクスとともに一覧表示されます。
