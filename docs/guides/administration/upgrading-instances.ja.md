# 稼働中のインスタンスをアップグレードする

このガイドでは、稼働中の Dependency-Track クラスターを、計画的なダウンタイムなしで新しいバージョンにアップグレードする方法を説明します。特定のリリース間の破壊的変更については、作業を始める前に必ず[リリースごとのアップグレードガイド](../upgrading/index.md)を確認してください。

## インプレースでアップグレードできる場合 {#when-you-can-upgrade-in-place}

永続実行エンジン、リーダー選出、[ロックフリーなタスクの取得](../../concepts/architecture/deployment.md#task-distribution)の仕組みにより、次の条件を満たしていれば API サーバーのインスタンスを 1 つずつ安全に置き換えられます。

- 間にあるすべてのバージョンのアップグレードガイドに、破壊的なスキーマ変更が記載されておらず、全停止の時間帯も求められていないこと。
- 複数のインスタンスが稼働していること。インスタンスが 1 つだけのデプロイでは、ダウンタイムなしでアップグレードできません。

これらの条件のいずれかを満たさない場合は、代わりに全停止によるアップグレードの時間帯を計画してください。

## 始める前に {#before-you-start}

- データベースをバックアップし、バックアップを検証します。[バックアップと復元](backing-up.md)を参照してください。
- 稼働中のバージョンから対象バージョンまでの間にあるすべてのバージョンのリリースノートを読みます。いずれかのリリースで全停止によるアップグレードが求められている場合は、作業を中止して全停止によるアップグレードを計画してください。
- 新しいイメージタグを選びます。スナップショットや `latest` ではなく、完全な `X.Y.Z` のリリースタグに固定してください。[コンテナーイメージ](../../reference/container-images.md)を参照してください。
- スキーマのマイグレーションを専用のコンテナーで実行する場合は、新しいバージョンの API サーバーが起動する前に実行するように計画します。[初期化専用コンテナー](../../reference/configuration/init-tasks.md#init-only-containers)を参照してください。
- PgBouncer のトランザクションモードで接続をプールしている場合、マイグレーションには PostgreSQL への直接接続が必要です。[初期化タスクのデータソース](../../reference/configuration/init-tasks.md#data-source)を参照してください。

## ローリングアップグレード {#rolling-upgrade}

1. スキーマのマイグレーションを実行します。専用のコンテナーで実行するか、新しいバージョンの最初のインスタンスに起動時に実行させます。

    !!! warning "先に起動プローブの猶予時間を引き上げる"
        マイグレーションが終わるまで起動は完了しません。マイグレーションが[起動プローブ](configuring-observability.md#configuring-kubernetes-health-probes)の許容時間(`failureThreshold` と `periodSeconds` の積)より長くかかると、オーケストレーターがマイグレーションの途中でインスタンスを再起動します。同時に起動したインスタンスは[初期化ロックを待機します](../../reference/configuration/init-tasks.md#lifecycle)が、この待機時間も同じ猶予時間に含まれます。リリースごとのアップグレードガイドでマイグレーションの所要時間に関する警告を確認し、両方をカバーできるように猶予時間を引き上げてください。[初期化専用コンテナー](../../reference/configuration/init-tasks.md#init-only-containers)でマイグレーションを実行すれば、この問題を回避できます。長時間稼働するコンテナーが、マイグレーション済みのスキーマに対して起動するためです。

2. プラットフォームのローリングアップデートの仕組みを使って、API サーバーのインスタンスを 1 つずつ置き換えます。

    各インスタンスが正常にシャットダウンできるよう、十分な時間を確保してください。正常に停止したインスタンスは、処理中のバックグラウンドタスクをキューに戻し、別のインスタンスが数秒以内にそれらを取得します。強制終了されたインスタンスは、ロックの有効期限が切れるまでそれらのタスクをロックしたままにするため、タスクのロックタイムアウトの期間だけ処理が遅れます。[タスクの処理](../../concepts/architecture/design/durable-execution.md#task-processing)を参照してください。

ロールアウトが完了するまで、古いインスタンスと新しいインスタンスがマイグレーション済みのスキーマに対して並行して稼働します。ロールアウトは 1 回のデプロイ時間帯内に収めてください。クラスターで異なるバージョンが混在する状態を無期限に放置しないでください。

## Web とワーカーの分離 {#webworker-split}

クラスターで [API のトラフィックとワーカーのトラフィックを分離している](scaling.md#separate-api-traffic-from-background-work)場合は、両方のグループを同じく 1 つずつ置き換える方法でアップグレードします。ワーカーを先にアップグレードしてください。ワーカーは自身が登録したタスクの種類だけをポーリングするため、新しいバージョンの API 層がキューに追加したタスクは、それを実行できるワーカーが現れるまでキューに残ります。

## ロールバックする {#rolling-back}

Dependency-Track はスキーマのマイグレーションを元に戻しません。マイグレーションを実行した後に以前のバージョンに戻すには、作業開始前に取得したデータベースのバックアップを復元し、そのデータベースに対して以前のバージョンを起動する必要があります。このことを念頭に置いてアップグレードの時間帯を計画してください。[バックアップと復元](backing-up.md#version-considerations)を参照してください。

## 全停止によるアップグレードに切り替えるべき場合 {#when-to-fall-back-to-a-full-stop-upgrade}

次の場合は、全停止によるメンテナンスの時間帯を計画してください。

- リリースノートで明示的に求められている場合。
- 稼働中のバージョンが読み書きするテーブルを、マイグレーションが書き換えたりロックしたりする場合。新しいテーブルだけを対象とする長時間の処理(バックフィルなど)は起動時間を延ばしますが、クラスターを停止する必要はありません。
- 作業中に少なくとも 1 つのインスタンスが稼働し続けることを保証できない場合。
