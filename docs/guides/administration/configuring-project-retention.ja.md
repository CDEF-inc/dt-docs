# プロジェクトの保持期間を設定する

スケジュールされたメンテナンスタスクは、保持ポリシーに従って**非アクティブ**なプロジェクトを削除できます。デフォルトでは、このタスクはオフです。このガイドでは、タスクの動作、ポリシーの選び方、設定方法を説明します。

プロジェクトを非アクティブにすることの意味については、[プロジェクトのバージョンを管理する › 古いバージョンを廃止する](../user/managing-project-versions.md#retire-an-old-version)と [About projects › Retention](../../concepts/projects.md#retention) を参照してください。

## タスクの動作 {#what-the-task-does}

メンテナンスタスクは定期的に実行され、保持がオンの場合、廃止された時期が設定したポリシーの範囲外にある非アクティブなプロジェクトを削除します。削除のたびに、アプリケーションログに 1 行が書き込まれます。

アクティブなプロジェクトには一切触れません。プロジェクトを非アクティブにすることが削除対象になる条件です。プロジェクトが非アクティブになると、以下のポリシーによって残すかどうかが決まります。

削除は元に戻せません。プロジェクトとともに、そのコンポーネント、監査履歴、プロパティ、アクセスリストも削除されます。

## ポリシーを選ぶ {#pick-a-policy}

2 つのモードがあります。どちらか 1 つを選びます。

### 経過日数で選ぶ {#by-age}

廃止されてから指定した日数を超えた非アクティブなプロジェクトを削除します。UI ではこのモードは *Age* と表示され、しきい値の日数を指定するスライダーがあります(デフォルトは 30)。

「古さ」が適切な基準である場合、つまり十分前に廃止されたプロジェクトはもう関心の対象ではない場合に使います。

### バージョン数で選ぶ {#by-version-count}

プロジェクト名ごとに、最近の非アクティブなバージョンを残し、それ以外を削除します。新しさは、各プロジェクトが非アクティブになった時刻で判断します。UI ではこのモードは *Versions* と表示され、残すバージョン数を指定するスライダーがあります(デフォルトは 2)。

プロジェクトが非アクティブになってからの期間にかかわらず、上限のあるアーカイブ(「廃止されたリリースのうち直近の 2 つを常に残す」など)が必要な場合に使います。

## 設定する {#configure-it}

*Administration > Configuration > Maintenance* を開き、*Projects Retention* セクションを見つけます。

1. *Enable Inactive Project Deletion* をオンにします。
2. *Project Retention Type* として *Age* または *Versions* を選択します。
3. 選択したモードのスライダー(日数またはバージョン数)を設定します。
4. 保存します。変更によってタスクが削除する範囲が広がる場合は、*Destructive Action Confirmation* ダイアログが表示されます。確認して適用します。

## 保持をオフにする {#turn-retention-off}

同じパネルで *Enable Inactive Project Deletion* をオフにします。次にメンテナンスタスクが実行されると、保持がオフであることをログに記録し、何も削除しません。

## 削除に伴って失われるもの {#what-deletion-takes-with-it}

プロジェクトを削除すると、そのプロジェクトに属するすべてのものが連鎖的に削除されます。具体的には、コンポーネントとサービス、依存関係グラフ、監査履歴(分析、コメント、抑制)、プロジェクトのプロパティ、プロジェクトへのタグの付与、アクセスリストのエントリーです。プロジェクト間で共有されるリソースは影響を受けません。タグ自体は残ります(孤立したタグは、後で[タグのメンテナンスタスク](../../concepts/tags.md#lifecycle)によって削除されます)。脆弱性のレコードは残り、共有データを参照していた他のプロジェクトも引き続き参照します。Dependency-Track には論理削除も取り消しもありません。

## 運用上の注意 {#operational-notes}

- アクティブなプロジェクトには一切触れません。プロジェクトを削除の対象にする唯一の方法は、非アクティブにすることです。
- タスクはバッチ単位で処理するため、オンにした後の最初の実行ではしばらく時間がかかることがあります。削除のたびにログ行が出力されるので、ログを追跡してデプロイメントを監査してください。
- タスクはデータベースロックを取得するため、スケールアウトしたデプロイメントでも、タスクを実行する API サーバーは一度に 1 つだけです。
- Dependency-Track は、削除されるまでは通常の流れの一部としてプロジェクトの通知を発火します。削除そのものではポートフォリオの通知は発行されません。
