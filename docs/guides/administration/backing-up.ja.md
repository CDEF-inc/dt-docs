# バックアップと復元

## バックアップの対象 {#what-to-back-up}

| コンポーネント | 保持する内容 | バックアップの方法 |
| --- | --- | --- |
| PostgreSQL | すべてのプロダクトデータ、永続実行エンジンの状態、監査履歴。 | 論理バックアップ(`pg_dump`)または物理バックアップ(PITR)。 |
| ファイルストレージ | 短期間だけ存在する中間ファイル(アップロードされた BOM、分析の成果物)。 | 任意。失われた場合、処理中のアップロードは再試行が必要です。 |
| 設定 | 環境変数、シークレットの参照。 | ソース管理するか、テンプレートから生成します。実行時のバックアップの対象ではありません。 |

失われると復旧できないコンポーネントはデータベースだけです。

## データベースをバックアップする {#back-up-the-database}

マネージド PostgreSQL では、プロバイダーの機能で自動バックアップとポイントインタイムリカバリー(PITR)を有効にします。セルフホストの PostgreSQL では、標準の[バックアップと復元](https://www.postgresql.org/docs/current/backup.html)の手順に従います。

`dt.dex-engine.datasource.name` が[別のデータベース](scaling.md#isolate-the-engine-database)を指している場合は、両方をバックアップします。2 つのデータベースは独立しているため、一方だけを復元するとエンジンの状態がプロダクトの状態と食い違います。共通のタイムスタンプへの PITR を使うか、API サーバーを停止してから、整合の取れた論理ダンプを取得します。

## バージョンに関する注意事項 {#version-considerations}

バックアップを作成したバージョンと同じか、それより新しいバージョンの Dependency-Track に復元し、初回起動時にスキーマのマイグレーションを実行させます。Dependency-Track は、古いバージョンへのダウングレードを伴う復元をサポートしていません。

## 復元後の作業 {#after-restoring}

データベースを復元し、すべての API サーバーを停止したら、次の手順を実行します。

1. インスタンスを 1 つ起動します。ポート `9000` の `/health/ready` が `UP` を返すまで待ち、スキーマのマイグレーションが問題なく適用されたことを確認します。その後、残りのインスタンスを起動します。
2. データベースを復元すると、ワークフローの状態はスナップショットの時点まで巻き戻ります。エンジンは実行中だった実行を自動的に再開します。スナップショットより後に作成された実行は存在しなくなるため、クライアントが再度トリガーする必要があります。全体のモデルについては [Durable execution](../../concepts/architecture/design/durable-execution.md) を参照してください。

ファイルストレージを個別にバックアップしている場合は、データベースと同じ時点に復元します。そうしないと、スナップショットの時点で処理中だったアップロードは失敗し、クライアントが再試行します。
