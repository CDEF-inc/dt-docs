# ワークロード ID

!!! note "5.2.0 以降で利用可能"

    それより前のバージョンでは、自動化処理の認証にはチーム API キーしか使えません。

モデルについては、[ワークロード ID フェデレーションについて](../concepts/workload-identity-federation.md)を参照してください。手順については、[ワークロード ID フェデレーションを設定する](../guides/administration/configuring-workload-identity-federation.md)を参照してください。

フィールドの制約、リクエストボディ、レスポンス、各操作に必要な権限は、[REST API v2 リファレンス](api/v2.md)の、`Workload Identity Providers` と `OAuth` のタグが付いた操作、および `Service Accounts` のタグが付いたワークロード ID バインディングの操作に記載されています。このページでは、それらの操作の背後にある動作を説明します。

## プロバイダーのタイプ {#provider-types}

| タイプ     | `iss` クレーム                      | `sub` クレーム                                | 鍵の取得元                          |
|:---------|:---------------------------------|:-------------------------------------------|:------------------------------------|
| `OIDC`   | プロバイダーの issuer と一致する必要がある | 任意の値                                  | ディスカバリー、キーセットの URL、またはインライン |
| `SPIFFE` | 無視される                          | `spiffe://<trust-domain>/` で始まる必要がある | バンドルエンドポイントの URL、またはインライン    |

`SPIFFE` プロバイダーの issuer は、`example.org` のような trust domain そのものです。`SPIFFE` プロバイダーのキーセットの URL は trust domain のバンドルエンドポイントであり、SPIFFE フェデレーションの `https_web` プロファイルを使う必要があります。

## 鍵の取得 {#key-fetching}

ディスカバリーは `<issuer>/.well-known/openid-configuration` を読み取り、そのドキュメントが同じ issuer を示していることを要求し、ドキュメントが示す `jwks_uri` を保存します。URL から鍵を取得する `OIDC` プロバイダーの issuer を変更すると、更新で鍵の取得元自体を指定していない限り、ディスカバリーが再実行され、保存されている URL が置き換えられます。

Dependency-Track は取得したキーセットをキャッシュし、プロバイダーごとに更新の頻度をレート制限します。更新に失敗した場合は、最後に取得したキーセットを最大 1 時間使い続けます。

### 外部への取得の制約 {#outbound-fetch-constraints}

Dependency-Track は、プロバイダーを保存するときと、交換の際に鍵がキャッシュにない場合に、リモートのドキュメントを取得します。すべての取得は次の制約に従います。

* ユーザー情報を含まない `https` の URL だけを使います。
* ホスト名を解決した後、Dependency-Track はループバック、リンクローカル、ワイルドカード、マルチキャストのアドレスを拒否します。プライベートアドレスの範囲は引き続き許可されます。設定された HTTP プロキシが宛先を扱う場合は、プロキシが名前を解決するため、Dependency-Track はアドレスのチェックを省略します。
* Dependency-Track はリダイレクトに従いません。
* レスポンスは 10 秒以内にすべて届く必要があり、1 MiB を超えてはいけません。
* レスポンスボディが API のレスポンスやログに含まれることはありません。

## サブジェクトの照合 {#subject-matching}

サブジェクトは、完全一致の値か、プレフィックスの後に `*` を続けたもののいずれかです。プレフィックスは空であってはならず、`:` または `/` で終わる必要があります。

| サブジェクト                                 | 一致するもの                                           |
|:----------------------------------------|:--------------------------------------------------|
| `repo:acme-inc/app:ref:refs/heads/main` | その値と完全に一致する `sub` クレーム。                           |
| `repo:acme-inc/*`                       | `repo:acme-inc/` で始まるすべての `sub`。       |
| `repo:acme-inc/app*`                    | 拒否されます。プレフィックスが `:` または `/` で終わっていません。 |
| `spiffe://example.org/ci/*`             | `spiffe://example.org/ci/` 配下のすべての SPIFFE ID。 |
| `spiffe://example.org/ci*`              | 拒否されます。SPIFFE のプレフィックスは `/` で終わる必要があります。      |

`SPIFFE` プロバイダーでは、サブジェクトはプロバイダーの trust domain の中にある必要があります。

セグメントの途中で終わるプレフィックスで照合するには、完全なサブジェクトのプレフィックスに、`claims.sub.startsWith("repo:acme-inc/app-")` のような条件を組み合わせます。

## 条件の環境 {#condition-environment}

条件は [CEL](cel-expressions.md) 式です。Dependency-Track は、バインディングを保存するときに条件をコンパイルし、型チェックします。条件から参照できる変数は 1 つです。

| 変数 | 型               | 内容                                  |
|:---------|:-------------------|:------------------------------------------|
| `claims` | `map(string, dyn)` | 検証済みのサブジェクトトークンのクレーム。 |

[CEL の strings 拡張](https://github.com/google/cel-spec/blob/master/doc/extensions/strings.md)を利用できます。Dependency-Track は、ここではカスタム関数を登録しません。

式はブール値を返す必要があります。クレームの値は動的なため、`claims.admin` だけではコンパイルできません。代わりに `claims.admin == true` と記述します。

交換時に、たとえばクレームが存在しないためにエラーになった条件は、一致しないものとして扱われます。クレームを省略したトークンにもバインディングを一致させたい場合は、省略可能なクレームを `has(claims.name)` で保護します。クレームの値は JSON の型を保持するため、ブール値を文字列としてエンコードするプラットフォームでは、文字列として比較する必要があります。

```js
claims.ref == "refs/heads/main"

claims.environment == "production" && claims.environment_protected == "true"

claims.sub.startsWith("repo:acme-inc/app-")
```

## 照合の順序 {#matching-order}

Dependency-Track が評価するのは、リクエストで指定されたサービスアカウントのバインディングのうち、指定されたプロバイダーに属するものだけです。それらを古いものから新しいものの順に試し、サブジェクトと条件の両方が一致した最初のバインディングを使います。重複するバインディングや重なり合うバインディングがあっても問題はありません。どちらの場合も、得られるセッションは同じだからです。

## サブジェクトトークンの要件 {#subject-token-requirements}

サブジェクトトークンは、次の要件を満たす署名付き JWT である必要があります。

| プロパティ            | 値                                                                                  |
|:--------------------|:---------------------------------------------------------------------------------------|
| ヘッダーの `typ`        | `JWT`、`JOSE`、`at+jwt`、または省略。                                                    |
| 署名アルゴリズム | `RS256`、`RS384`、`RS512`、`PS256`、`PS384`、`PS512`、`ES256`、`ES384`、`ES512` のいずれか。    |
| 必須のクレーム     | `exp` と `sub`。                                                                       |
| `aud`               | プロバイダーの audience を含む必要があります。                                                  |
| `iss`               | `OIDC` プロバイダーでは、プロバイダーの issuer と一致する必要があります。`SPIFFE` プロバイダーでは無視されます。 |

Dependency-Track は、対称鍵で署名されたトークンと署名のないトークンを拒否します。署名用としてマークされた鍵に加えて、SPIFFE バンドルがマークするように `jwt-svid` 用としてマークされた鍵も受け付けます。

## 監査イベント {#audit-events}

API サーバーは、次の操作をセキュリティイベントとしてログに記録します。

* プロバイダーとバインディングの作成、更新、削除。
* 成功した交換。プロバイダー、サービスアカウント、一致したバインディング、トークンのサブジェクト、および `jti` があればその値を記録します。
* 拒否された交換。トークンは検証できたものの一致するバインディングがなかった場合は、トークンのクレームもログに含まれます。

サブジェクトトークンがログに記録されることはありません。
