# 通知について

## はじめに {#introduction}

Dependency-Track には、プラットフォーム内のイベントをユーザーや外部システムに知らせる、設定可能な通知フレームワークが含まれています。

## アラート {#alerts}

アラート(*通知ルール*)は、どの通知をどの送信先に送るかを指定する設定です。アラートは、サブスクライブする通知のスコープ、グループ、レベルを定義し、必要に応じて照合を特定のプロジェクトやタグに限定します。

[CEL] で記述する*フィルター式*を使うと、アラートをさらに絞り込めます。この式は各通知の内容に対して評価されるため、フィルター条件ごとに専用の UI コントロールがなくても、脆弱性の深刻度、CVSS スコア、コンポーネント名などのプロパティで絞り込めます。詳しくは [Filter expressions](../reference/notifications/filter-expressions.md) を参照してください。

## パブリッシャー {#publishers}

パブリッシャーは、プラットフォームが発行した通知を送信先のシステムに配信するソフトウェアコンポーネントです。Dependency-Track には、メールから Webhook まで、さまざまなパブリッシャーが付属しています。詳しくは [Publishers](../reference/notifications/publishers.md) を参照してください。

## テンプレート {#templates}

テンプレートは、プラットフォーム内部での通知の表現([Notification schema](../reference/notifications/schema.md) を参照)を、通知の受信者が想定する形式にどう対応付けるかを定義します。

各[パブリッシャー](#publishers)にはデフォルトのテンプレートが付属しており、管理者はカスタムテンプレートを設定できます。テンプレートで使える変数とフィルターについては、[Templating](../reference/notifications/templating.md) を参照してください。

## レベル {#levels}

通知は次の 3 つのレベルのいずれかを持ちます。

* Informational
* Warning
* Error

これらのレベルはログレベルと同じように動作し、[アラート](#alerts)で送信する通知の詳細度を定義できます。

* レベル *Informational* に設定したアラートは、レベル *Informational*、*Warning*、*Error* の通知に一致します。
* レベル *Warning* に設定したアラートは、レベル *Warning* と *Error* の通知に一致します。
* レベル *Error* に設定したアラートは、レベル *Error* の通知にのみ一致します。

## スコープ {#scopes}

通知は*スコープ*を持ちます。スコープは、通知の*サブジェクト*を大まかに分類します。

* **SYSTEM**: ユーザーの作成や連携の失敗など、システムレベルのイベントを知らせます。
* **PORTFOLIO**: BOM のアップロードや新たに特定された脆弱性など、ポートフォリオレベルのイベントを知らせます。

## グループ {#groups}

グループは、[スコープ](#scopes)内で通知のサブジェクトを細かく分類したものです。たとえば、`PORTFOLIO` スコープ内の `NEW_VULNERABILITY` グループは、システムが新しい脆弱性を見つけるたびに発行する通知を表します。

グループ、そのスコープ、レベル、トリガーの完全な一覧については、[Notification groups](../reference/notifications/groups.md) を参照してください。

## トリガー {#triggers}

プラットフォームは、次の 2 つのトリガーのいずれかによって通知を生成します。

| トリガー | 説明                                                       |
|:---------|:-----------------------------------------------------------|
| Event    | 特定の条件のもとでシステムがイベントを発行します。         |
| Schedule | 計画されたスケジュールに従って通知が発火します。           |

* イベントでトリガーされる通知は、ほぼリアルタイムの自動化やチャットプラットフォームとの連携に適しています。
* スケジュールされた通知は通常、概要レベルのサマリーを伝えるため、レポートにより適しています。

各[グループ](#groups)がサポートするトリガーの種類は 1 つだけです。ほとんどのグループはイベントトリガーを使い、サマリーのグループ(`NEW_VULNERABILITIES_SUMMARY`、`NEW_POLICY_VIOLATIONS_SUMMARY`)はスケジュールトリガーを使います。

## アラートのフィルタリングのしくみ {#how-alert-filtering-works}

プラットフォームは、通知をディスパッチするときに、アラートのフィルターを次の順序で適用します。

1. スコープ、グループ、レベルの照合。
2. アラートが配信を特定のプロジェクトやタグに限定している場合は、プロジェクトとタグによる制限。
3. アラートに[フィルター式](../reference/notifications/filter-expressions.md)がある場合は、その式。

プラットフォームがフィルター式を実行するのは、通知がそれより前のチェックを通過した後だけです。そのため、式の内容にかかわらず、プロジェクトとタグによる制限は常に適用されます。

フィルター式は *fail-open* です。たとえばサブジェクトに存在しないフィールドにアクセスしたことが原因で、ディスパッチ時に式の実行が失敗した場合でも、アラートは通知に一致したものとして扱われます。これにより、式が壊れたときに通知が気付かれないまま送信されなくなることを防ぎます。評価の失敗は警告としてログに記録されます。式が常に失敗するアラートは、フィルター式がまったくないかのように動作します。
