# コンポーネントポリシーについて

コンポーネントポリシーを使うと、サードパーティのコンポーネントが満たすべき基準を組織としてルール化し、コンポーネントが基準を満たさないたびに*違反*として表面化させることができます。典型的な用途には、コピーレフトライセンスの禁止、コンポーネントが数年以内のものであることの要求、特定のパッケージ座標のブロック、上流からメジャーバージョンが 1 つより多く遅れているものがないことの確認などがあります。

[脆弱性ポリシー](vulnerability-policies.md)が個々の脆弱性の検出結果に作用してそれに分析を適用するのに対し、コンポーネントポリシーはコンポーネントそのものに作用します。両者は補完的です。許容できるコンポーネントの条件を表すにはコンポーネントポリシーを使い、個々の検出結果に対するトリアージの判断を一元化するには脆弱性ポリシーを使います。どちらも同じ式言語、評価コンテキスト、カスタム関数ライブラリを共有します。詳しくは[条件式](../reference/policies/condition-expressions.md)を参照してください。

## 違反の意味 {#what-a-violation-means}

違反は、`(component, project, condition)` の 3 つ組に対して記録される事実です。すべての違反は、ポリシーの*違反の状態*(`INFO`、`WARN`、`FAIL` のいずれか)を引き継ぎます。この状態は、プロジェクトのメトリクス、プロジェクトのバッジ、[`POLICY_VIOLATION` 通知グループ](../reference/notifications/groups.md)に伝播します。組織では通常、`FAIL` の違反を使って CI/CD パイプラインを失敗させます。

違反は監査できます。脆弱性の検出結果と同様に、各違反は抑制、コメント、分析状態をサポートします。監査証跡は違反とともに保存され、再評価をまたいで保持されます。

利用できる分析状態は `APPROVED`、`REJECTED`、`NOT_SET` です。Dependency-Track は `APPROVED` や `REJECTED` に固定の意味を持たせておらず、どのような規約にするかはチームが決めます。よく使われる規約は 2 つあります。*リスク受容*(`APPROVED` はチームがその違反を受け入れたことを表し、抑制と組み合わせて使います)と、*ワークフロー*(`APPROVED` は対応が必要な違反を、`REJECTED` は対応が不要な違反を表します)です。どちらか 1 つを選び、文書化してください。分析状態の設定方法については、[ポリシー違反をトリアージする](../guides/user/triaging-policy-violations.md)で説明しています。

## ポリシーの判定のしくみ {#how-a-policy-decides}

ポリシーは 1 つ以上の*条件*と、それらを組み合わせる演算子を持ちます。演算子が `ANY` の場合は 1 つの条件が一致すれば違反が発生し、`ALL` の場合はすべての条件が一致する必要があります。

条件は、何を調べるかを表します。組み込みのサブジェクトは 3 つの系統に分かれます。

- **ライセンス**系のサブジェクト(`LICENSE`、`LICENSE_GROUP`)は、コンポーネントの解決済みのライセンス、またはライセンスグループへの所属に基づいて一致します。
- **運用**系のサブジェクト(座標、パッケージ URL、ハッシュ、経過期間、バージョン、バージョン距離、SWID タグ)は、コンポーネントの識別情報とライフサイクルに基づいて一致します。
- **セキュリティ**系のサブジェクト(深刻度、CPE、CWE、EPSS スコア、脆弱性 ID)は、コンポーネントの脆弱性に基づいて一致します。

組み込みのサブジェクトでは表現できないものについては、ポリシーで *Expression* サブジェクトを使用できます。これは、コンポーネント、プロジェクト、コンポーネントの脆弱性、現在時刻を対象に評価される [CEL](../reference/cel-expressions.md) 式です。脆弱性ポリシーで使われるのと同じ式言語であり、同じカスタム関数([`spdx_expr_allows`](../reference/policies/condition-expressions.md#spdx_expr_allows)、[`is_dependency_of`](../reference/policies/condition-expressions.md#is_dependency_of)、[`matches_range`](../reference/policies/condition-expressions.md#matches_range)、[`version_distance`](../reference/policies/condition-expressions.md#version_distance) など)を使えます。式による条件を使うと、コンポーネントのフィールドを組み合わせたり、依存関係グラフをたどったり、SPDX ライセンス式を直接操作したりするルールを組織としてルール化できます。式は `true` の代わりにメッセージを返すこともでき、その場合、発生した違反で何が一致したかを説明できます。[結果](../reference/policies/condition-expressions.md#result)を参照してください。

## ポリシーの適用範囲 {#where-a-policy-applies}

デフォルトでは、ポリシーはポートフォリオ内のすべてのプロジェクトに適用されます。特定のプロジェクト、それらのプロジェクトの子孫、または特定の[タグ](tags.md)が付いたプロジェクトに絞り込むことができます。スコープはフラットで、ポリシーはプロジェクトに適用されるか、されないかのどちらかです。正確なルールについては、[コンポーネントポリシー › 割り当て](../reference/policies/component-policies.md#assignment)を参照してください。

## ライフサイクル {#lifecycle}

プロジェクトの分析は、BOM が届いたとき、定期的にスケジュールされたポートフォリオ分析の実行中、および手動でトリガーしたときに、ポリシーを評価します。各実行では、違反をプロジェクトの現在の状態と突き合わせます。新たに一致したものは違反となって通知を発行し、一致しなくなった以前の違反はエンジンが削除します。このため、ポリシーを段階的に作成しても問題ありません。ライセンスの許可リストを厳しくすれば違反が増え、緩めれば違反が減り、監査証跡にはその両方が反映されます。

!!! warning "ポリシーの編集はすぐには反映されません"
    ポリシーを保存または編集しても、その時点で分析が再実行されるわけではありません。既存の違反は、各プロジェクトの次回のプロジェクト分析まで残ります。次回の分析は、次の BOM のアップロード、次回のスケジュールされたポートフォリオ分析、または手動のトリガーで実行されます。

!!! note "非同期に取り込まれるデータ"
    条件の入力の中には、分析の開始後に Dependency-Track が外部ソースから解決するデータに由来するものがあります。コンポーネントの公開日、把握している最新バージョン、EPSS スコア、脆弱性のメタデータです。アップロードされたばかりの BOM を初めて評価するときは、これらのフィールドがまだ空の場合があり、それらを読み取る条件(`AGE`、`VERSION_DISTANCE`、`EPSS`、および同じデータを参照する式)は一致しません。バックグラウンドのタスクが完了すると、次の評価から一致するようになります。リリースの可否を判定するポリシーは、この点を踏まえて計画してください。

## ライセンスグループ {#license-groups}

ライセンスグループは、ライセンスの集合に名前を付けたものです(たとえば *Copyleft* や *Permissive*)。一般的なものはプラットフォームが初期登録しており、運用者が拡張できます。グループを使うと、ライセンスポリシーが読みやすくなります(数十個の識別子を列挙する代わりに *"License is in Copyleft"* と書けます)。`OR` 演算子や `WITH` 演算子を含む SPDX 式や、バージョンを考慮した照合など、より高度なルールには、[`spdx_expr_allows`](../reference/policies/condition-expressions.md#spdx_expr_allows) を使った `Expression` 条件を使用します。
