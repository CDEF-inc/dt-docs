# v5 での変更点について

Dependency-Track v5 では、プラットフォームを大幅にリファクタリングしています。書き直したわけではありません。基盤となる技術やサブシステムの多くは、v4 から手を加えずに引き継いでいます。変更の大半は、v4 の設計が限界を示していた部分、つまりスケーラビリティと信頼性、ポリシーエンジン、運用の複雑さに対処するものです。いくつかのセクションでは、v4 にはまったくなかった新しい機能を扱います。

このページでは、*何が変わったのか、なぜ変わったのか*をまとめます。アップグレードの具体的な手順については、[アップグレードガイド](../guides/upgrading/index.md)を参照してください。既存の v4 のデプロイから v5 にデータを移すには、[v4 から v5 に移行する](../guides/administration/migrating-from-v4.md)を参照してください。

## v5 を作った理由 {#why-v5}

v4 は単一の API サーバーとして動作し、そのサーバーがインメモリーのキューとローカルの Lucene インデックスを保持していました。データベースは運用者が選んだものを使用していました。この形は小規模なデプロイには合っていましたが、高可用性、予測可能なリソース使用量、部分的な障害からの復旧を必要とする場合には制約となっていました。

v5 はこれらの制約に直接取り組みます。プラットフォームは水平にスケールし、クラッシュしても処理を失わず、成熟した単一のデータベースエンジンに絞り込みました。小規模なデプロイも引き続き動作し、同じ保証を得られます。

## 何が変わったのか、なぜ変わったのか {#what-changed-and-why}

### 高可用性と永続的なバックグラウンド処理 {#high-availability-and-durable-background-work}

v5 では、v4 のプロセス内にあった単一障害点(インメモリーのキューとローカルインデックス)を取り除きました。Web ノードとワーカーノードは個別にスケールし、バックグラウンド処理はインメモリーのプールではなく、PostgreSQL を基盤とするキューを通じて分散されます。PostgreSQL の高可用性は引き続き利用者の責任です。[Dependency-Track のスケーリング](../guides/administration/scaling.md)を参照してください。

長時間実行される処理(BOM の処理、脆弱性分析、通知の配信)は、[永続実行エンジン](architecture/design/durable-execution.md)上で実行されます。タスクは JVM とともに消えるのではなく、再起動やクラッシュの後に中断した箇所から再開します。失敗したステップは、手動で再実行する必要はなく、指数バックオフで自動的にリトライされます。

通知も同じモデルに従います。ランタイムは、通知のきっかけとなった変更と同じトランザクションで、各通知を[トランザクショナルアウトボックス](architecture/design/notifications.md)に書き込みます。その後、リレーが非同期に配信します。配信の保証は at-least-once になります。受信側は重複を許容する必要がありますが、処理の途中でイベントが知らないうちに消えることはありません。ユーザーから見たモデルについては、[通知について](notifications.md)を参照してください。

### PostgreSQL に一本化したデータプレーン {#a-single-data-plane-on-postgresql}

v5 は PostgreSQL に絞り込み、H2、MySQL、Microsoft SQL Server のサポートを終了しました。1 つのエンジンに集中することで、v4 のマルチデータベースの抽象化では使えなかった PostgreSQL 固有の機能を使えるようになりました。スキーマの変更は、実行時のオブジェクトリレーショナルマッパー(ORM)による差分検出ではなく、明示的でバージョン管理された変更履歴を通じて適用されるようになったため、アップグレードは予測可能で、きれいにロールバックできます。

v4 が別プロセスとして実行していた 2 つのサブシステムは、データベースの中に移りました。

* **検索**は PostgreSQL に対して直接実行されます。ディスク上の `~/.dependency-track/index` ディレクトリはなくなり、それに伴っていたインデックスの破損やディスク容量不足による障害もなくなりました。同時に、Lucene のあいまい一致も使えなくなりました。[変更による影響](#what-this-breaks)を参照してください。
* **キャッシュ**は引き続き PostgreSQL に置かれますが、`UNLOGGED` テーブルを使います。先行書き込みログのオーバーヘッドがなく、設計上、永続化されません。v4 はキャッシュの行を通常のテーブルに保存し、定期的なクリーンアップタスクだけで量を抑えていました。v5 はキャッシュごとに TTL を適用します。

メトリクスもデータベースに移りました。v4 は、特定時点のカウンターを Java のタスクで 1 行ずつ再計算していました。v5 はメトリクスを本来の時系列データとし、PostgreSQL の中で計算します。[時系列メトリクスについて](time-series-metrics.md)を参照してください。

スキーマでは、v4 がマルチデータベースの抽象化のためにアプリケーションのコードに任せていた制約を厳しくしました。より厳しい制約により、不正なデータが知らないうちに広がるのを許さず、永続化層で検出できます。

PostgreSQL に絞り込んだことで、的を絞ったパフォーマンス改善も可能になりました。よく使われるクエリーの形に対する部分インデックス、大量の時系列データに対するテーブルのパーティショニング、ネットワークと I/O のオーバーヘッドを減らすための読み取りと書き込みのバッチ化などです。

### CEL によるポリシーと通知のフィルタリング {#policies-and-notification-filtering-in-cel}

v4 のポリシーエディターでは、固定された演算子を使った条件のリストを作成していました。v5 では、同じエディターの裏側に、v4 よりも効率的で、評価に [Common Expression Language][CEL] を使う新しいエンジンを置いています。構造化された条件では足りない場合は、Expression 条件を使って CEL を直接記述できます。同じエンジンが[脆弱性ポリシー](vulnerability-policies.md)も動かしており、検出結果がフロントエンドに届いたり通知をトリガーしたりする前に、検出結果を監査または抑制できます。

CEL は[通知](notifications.md)にも使われます。v4 のアラートは、プロジェクト、タグ、レベル、グループでフィルタリングしていました。v5 のアラートは、アラートが持つ[フィルター式](../reference/notifications/filter-expressions.md)を通じて、通知ペイロードの任意のフィールドで照合できます。たとえば、指定した深刻度以上の脆弱性の場合にだけ発火するアラートを作成できます。

### コンポーネントの完全性検証 {#component-integrity-verification}

Dependency-Track は、上流のパッケージリポジトリが公開しているハッシュと一致しないハッシュを持つコンポーネントにフラグを立てます。このチェックにより、タイポスクワッティングやレジストリ側での改ざんといった、v4 ではチェーンのより下流にあるスキャナーに任せていた種類のサプライチェーン攻撃を検出できます。サポートしているエコシステムや、状態が UI とポリシーにどのように現れるかについては、[コンポーネントの完全性検証について](component-integrity-verification.md)を参照してください。

### ポートフォリオのアクセス制御がベータを終了 {#portfolio-access-control-out-of-beta}

[ポートフォリオのアクセス制御](access-control.md#portfolio-access-control)は、v4 ではベータ機能として提供されており、既知の不足があり、大規模なポートフォリオでは目立つオーバーヘッドがありました。v5 ではこれらの不足を解消し、プロジェクト数が増えてもコストが一定の範囲に収まるように実装を作り直しました。

### プロジェクトとメトリクスの保持ポリシー {#retention-policies-for-projects-and-metrics}

v5 は、非アクティブなプロジェクトのバージョンと時系列メトリクスを、設定可能なスケジュールで期限切れにします。v4 ではどちらも際限なく増えていたため、運用者は古いポートフォリオのデータと増え続けるメトリクスのテーブルを抱えていました。[プロジェクトの保持期間を設定する](../guides/administration/configuring-project-retention.md)と[時系列メトリクスの保持](time-series-metrics.md#daily-partitions-and-bounded-retention)を参照してください。

### シークレットの一元管理 {#centralized-secrets}

連携のための認証情報は、機能ごとの設定に散らばるのではなく、デプロイが選択したシークレットマネージャーのプロバイダーの背後で 1 か所にまとめられます。保存先が 1 つになることで、監査とローテーションが簡単になります。漏えいした認証情報は、散らばった設定画面ではなく 1 か所でローテーションできます。[シークレットを管理する](../guides/user/managing-secrets.md)を参照してください。

### 独立した管理用のインターフェース {#a-separate-management-surface}

v4 は、フレームワーク内部のカウンターを REST API と同じインターフェースで公開していました。v5 は専用の管理サーバーを別のポートで実行し、Prometheus メトリクスと Kubernetes 形式の liveness プローブと readiness プローブを提供します。これにより、スクレイプとプローブの対象は、ユーザー向けのトラフィックとは別のライフサイクルで扱われます。[オブザーバビリティを設定する](../guides/administration/configuring-observability.md)を参照してください。

### リソース使用量の削減 {#reduced-resource-footprint}

ランタイムは、同等のワークロードで v4 よりも少ないベースラインのメモリーと CPU を目標としています。その多くは、インメモリーのキュー、Lucene インデックス、v4 のメトリクス再構築ループを取り除いたことによるものです。

## 変更による影響 {#what-this-breaks}

これらの変更には、クライアント、連携、通知の受信側に対する破壊的変更が伴います。フィールド単位の詳細と対処手順を含む完全な一覧は、[アップグレードガイド](../guides/upgrading/index.md)にあります。主な項目は次のとおりです。

* **通知のスキーマ。** サブジェクトは [Protobuf][Protobuf] を使うようになりました([通知スキーマのリファレンス](../reference/notifications/schema.md)を参照)。リストのフィールドには `List` という接尾辞が付き、列挙型のような値には型の接頭辞が付きます(`INFORMATIONAL` → `LEVEL_INFORMATIONAL`、`SYSTEM` → `SCOPE_SYSTEM`、`NEW_VULNERABILITY` → `GROUP_NEW_VULNERABILITY`)。タイムスタンプはミリ秒精度の単一の形式にそろえられます。v4 の場当たり的なサブジェクトオブジェクトを使っていたテンプレートは、書き直す必要があります。
* **REST API v1。** いくつかのエンドポイントが削除され、レスポンスのスキーマが変わり、リストを返すエンドポイントではデフォルトでページネーションが適用されます。すべての一覧については、[v5 の破壊的変更](../reference/api/v5-breaking-changes.md) を参照してください。
* **あいまい一致による脆弱性分析。** v4 の内部アナライザーは、コンポーネントに CPE がない場合、オプションで、内部の脆弱性データベースに対する Lucene ベースのあいまい一致にフォールバックしていました。Lucene をなくしたことで、この機能は使えなくなりました。
* **配布形式。** v4 は、API サーバーとフロントエンドの個別のコンテナーイメージ、両方をまとめた「バンドル」コンテナーイメージ、実行可能な WAR を提供していました。v5 はコンテナーイメージのみを提供し、バンドルイメージは廃止しました。バンドルイメージや WAR を使っている運用者は、個別の API サーバーとフロントエンドのコンテナーに移行する必要があります。
* **NVD フィードのミラー。** v4 は、ダウンロードした NVD のフィードファイルを `/mirror/nvd/*` で公開しており、他のツールが Dependency-Track をローカルの NVD ミラーとして使えました。v5 はフィードファイルを保存しなくなりました(内部で使う用途がないため)。また、v5 のファイルストレージは、配信元としてローカルのファイルシステムを前提とせず、S3 などのバックエンドを抽象化しています。Dependency-Track はこのエンドポイントを提供しなくなりました。フィードは NIST から直接取得するか、専用のミラーを運用してください。社内の NVD や OSV のミラーをホストする方法については、[エアギャップ環境で運用する](../guides/administration/running-air-gapped.md)を参照してください。
