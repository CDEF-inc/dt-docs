# 時系列メトリクスについて

リスクの現在の状態を示すビューは、今何が問題になっているかには答えられます。しかし、チームが改善しているのか、どれくらいの速さで改善しているのかには答えられません。Dependency-Track は、この 2 つ目の問いに答えられるように時系列メトリクスを記録します。すべてのプロジェクト、コンポーネント、そしてポートフォリオ全体が測定値の履歴を残し、日、週、四半期の単位で、修正の進み具合、監査のスループット、セキュリティ態勢の変化を明らかにします。

## 差分ではなくスナップショット {#snapshots-not-deltas}

メトリクスのレコードは*スナップショット*です。これは、ある時点における脆弱性、[検出結果](vulnerability-findings.md)、抑制、監査の進み具合、ポリシー違反の完全な数を、1 つのコンポーネント、プロジェクト、またはポートフォリオを対象にまとめたものです。差分から傾向を再構成する方法は脆弱です(イベントを 1 つ取りこぼすと、それ以降の系列がすべて損なわれます)。そのため Dependency-Track は絶対値を保存し、差分は読み取る側で計算させます。

スナップショットであることは、後でユーザーが遭遇するいくつかの挙動の理由にもなっています。

* 抑制すると、その後に取得されるすべてのスナップショットから検出結果が除外されます。過去の系列には抑制前の古い数が残ります。これはまさに、セキュリティ態勢のグラフが示すべき内容です。
* 検出結果の監査状態(トリアージ中、影響なし、悪用可能)は次のスナップショットの監査済み/未監査の数に反映されるため、グラフにはスキャナーの出力だけでなく、人による作業の進み具合も反映されます。
* プロジェクトの継承されたリスクスコアは、そのコンポーネントのリスクから算出され、各プロジェクトのスナップショットに記録されます。ポートフォリオの合計はそれらのプロジェクト単位のスコアを合算したもので、ポートフォリオのメトリクスでは、読み取り時に子プロジェクトから値を再計算することはありません。

スコープごとの正確なフィールドの一覧は、[REST API リファレンス](../reference/api/v1.md)の `metrics` タグが付いたオペレーションに記載されています。

## スナップショットが書き込まれるタイミング {#when-snapshots-get-written}

プロジェクトとそのコンポーネントのスナップショットは、次の 2 つによって作成されます。

* **プロジェクトを変更するアクティビティ。** BOM のアップロード、脆弱性分析の実行、手動の再分析では、その処理の最後のステップとして新しいスナップショットが書き込まれます。アクティブなプロジェクトでは 1 日に多数のスナップショットが作成されるため、プロジェクトのアクティビティが多いほど系列の解像度が高くなります。
* **スケジュールされた一斉処理。** プラットフォーム全体のジョブが、固定のスケジュール(デフォルトでは 1 時間ごと)ですべてのアクティブなプロジェクトを処理するため、動きのないプロジェクトでも 1 日に少なくとも 1 つのスナップショットが作成されます。これにより、系列が途切れず、保持期間が予測どおりに機能することが保証されます。

ポートフォリオのスナップショットは異なります。その理由は、次の 2 つのセクションで説明します。

## 日単位のパーティションと有限の保持期間 {#daily-partitions-and-bounded-retention}

コンポーネントとプロジェクトのスナップショットは、何も削除しなければ際限なく蓄積されます。Dependency-Track は両方のテーブルを日単位でパーティション分割しているため、保持期間の処理は常に 1 つのパーティションの削除で済み、行のスキャンは発生しません。「1 日分のメトリクスを削除する」コストは、テーブルが 100 万行でも 10 億行でも変わりません。この設計によって粒度の上限が決まります(1 日未満の保持期間は設定できません)が、メトリクスが答えようとする分析上の問い(週ごと、四半期ごとの傾向)は、それよりはるかに粗い解像度で扱うものなので問題ありません。

保持期間は設定可能な期間で、デフォルトは 90 日です。1 時間ごとに実行されるメンテナンスタスクが、期間外のパーティションを削除し、今後の日のパーティションをあらかじめ作成します。管理者は、静的な起動時のプロパティではなく、フロントエンドまたは REST API から実行時にこの値を変更します。

![Administration > Configuration > Maintenance にある保持期間の設定](../assets/images/concepts/time-series-metrics/admin-maintenance-config.png)

この設計から、次の 2 つのことが言えます。保持期間を短くすると次のメンテナンスサイクルでディスク容量が解放されます。一方、保持期間を延ばしても影響するのはその時点以降に記録されるデータだけです。すでに期間外となった日のデータは存在しないためです。

## ポートフォリオのメトリクスが 2 つの経路をとる理由 {#why-portfolio-metrics-take-two-paths}

ダッシュボードを読み込むたびにポートフォリオ全体のリスクを集計すると、プロジェクトが数千を超えたあたりから性能が大きく低下します。Dependency-Track は事前計算したスナップショットによってこのコストを回避し、スナップショットで対応できないケースではその場での集計にフォールバックします。

* **制限のない呼び出し元**(デフォルトの状態で[ポートフォリオのアクセス制御](access-control.md#portfolio-access-control)がない場合、またはアクセス制御をバイパスするプリンシパル)は、ポートフォリオのメトリクスの実行のたびに更新される、事前計算済みのスナップショットから読み取ります。処理はすでにバックグラウンドで済んでいるため、ポートフォリオの規模にかかわらず読み取りは低コストです。
* **制限のある呼び出し元**(ポートフォリオのアクセス制御によってプロジェクトの一部に制限されている呼び出し元)は、代わりにその場での集計を使います。このクエリは、その呼び出し元がアクセスできるプロジェクトについて、日ごとのプロジェクトのスナップショットを合算します。表示対象の集合は構造上ポートフォリオ全体より小さいため、この処理は低コストに保たれます。スナップショットはポートフォリオ全体の合計を保持しており、呼び出し元ごとにフィルターされた合計ではないため、これらの呼び出し元には使えません。

コレクションプロジェクトは、継承されたリスクが読み取り時に解決されるのと同じ理由で、事前計算済みのスナップショットの対象外です。コレクションプロジェクトの数値は子の数値を合算したものなので、ポートフォリオの合計に含めると二重に数えてしまいます。

避けられないトレードオフとして、事前計算の経路はライブのデータから最大で 1 回の更新サイクル分遅れますが、その場での集計の経路は常に最新です。セキュリティ態勢の推移のグラフではこの違いは目立ちませんが、「直前のスキャンはもう反映されたか」を確認するときには、ときどき予想と異なる結果になります。
